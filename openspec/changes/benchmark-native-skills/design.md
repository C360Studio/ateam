# Design outline

## First establish the provider contract

Gemini is the first candidate because its documented native activation tool has a named skill argument. This is a design choice, not a claim that the benchmark's pinned Gemini CLI 0.43.0 supports every required behavior. Before implementation, inspect that installed/versioned contract and record discovery roots, activation consent in headless mode, settings/tool restrictions, event identity, success/failure semantics and usage retention. No inference is needed for contract/source inspection and synthetic fixtures; any paid validation needs separate authorization.

Official references: [activation tool](https://geminicli.com/docs/tools/activate-skill/) and [skill management](https://geminicli.com/docs/cli/using-agent-skills/). The documentation describes agent-requested activation and activation consent. It does not prove the pinned CLI's isolation or evidence contract. If exact-skill consent cannot be safely expressed, or native evidence cannot identify activation outcomes, record the unsupported boundary and revisit the design before implementing. Do not switch providers silently, enable broad approval bypass, execute scripts or replace native activation with injected prompt text.

## Smallest treatment surface

Reuse `Experiment`, `ResolvedExperiment`, bundle file validation/snapshot helpers, `RunExperiment`, native parsing, comparison and rescore. Likely callers are `internal/bench/experiment.go`, `bundle.go`, `experiment_run.go`, `gemini.go`, native event parsing and their tests, plus `cmd/ateam` only if configuration loading requires it. Fixtures and examples belong under `internal/bench/testdata` and `benchmarks/examples`; user documentation remains in `benchmarks/README.md`.

Design the optional per-arm skill selector and immutable evidence schema after contract inspection. It must coexist with existing ordinary instruction text/bundles without changing their meaning. Select exactly one local regular UTF-8 SKILL.md per arm using explicit confined paths, bounded bytes and anchored reads; reuse the existing resolver's safety conventions instead of a general package installer. Define concrete size/frontmatter limits in the reviewed schema before code. Support only name, description and declarative Markdown body. Reject unrecognized frontmatter that could alter tools, hooks, invocation policy or execution; no sidecar resources, scripts, recursive discovery, downloads or external includes. Treat body text as untrusted model instructions, never runner commands; text may mention other files but the runner does not fetch them or grant capabilities.

Use the same validated skill name and description, ordinary instructions and invocation wording for both arms. Model/provider/reasoning, native version, tools, prompt scaffold, task set, scheduling, turns and budget limits remain shared. A/B varies body bytes only; A/A requires identical bytes. Source paths/labels do not constitute a treatment difference and do not leak into the model prompt. A no-skill baseline, discovery-description experiments and mixed prompt/skill changes are later slices. Extend the existing effective-treatment check explicitly so equal ordinary instructions plus different skill bodies is valid A/B; preserve old prompt-only equality rules.

## Isolation and evidence

Snapshot exact skill bytes and hashes at resolution, validate them again before inference and stage only the selected arm in its fresh generated workspace/home. Keep existing API-key-only authentication, dotenv barriers, managed-policy refusal, context restrictions and limits. Permit only the reviewed skill activation surface in addition to existing read-only tools. Hooks, shells, MCP, extensions, extra skills and ambient user/project configuration stay disabled or cause refusal. Unsupported adapter selectors fail in resolution, before credentials or inference; this initial slice must not appear supported on Claude, Codex or generic command adapters.

Separate evidence layers: requested snapshot; runner-confirmed staged bytes; CLI discovery/loaded observations if exposed; identified activation request; identified successful or failed activation result. Each native observation must refer to retained trace evidence, including correlation identity where available. A request alone does not prove successful activation. File creation, a model's self-report or a generic tool count cannot establish activation. Missing, incomplete or truncated evidence stays unknown; unknown is not zero or false. A successful activation reports only the observed CLI action, not skill compliance or performance benefit.

Retain all scheduled attempts and their existing grading/status/usage, including failures, timeouts, missing activation and partial traces. Report skill evidence alongside independent task quality; do not discard unactivated attempts or select an activated-only winner. Keep partial usage and native failures visible under current accounting rules. Comparison and rescore must reconstruct skill evidence from saved snapshots/traces without reading original files or making model calls. Preserve older artifact replay and the existing overall artifact-size ceiling, including skill snapshot and trace overhead.

## Acceptance and calibration

Provide A/A and A/B dry-run examples with reviewable content hashes, fixed dimensions, capability restrictions and limits. Use literal trace fixtures as independent oracles for requested-only, successful, failed, unrelated-skill, duplicate/out-of-order, truncated and absent activation histories. Use a small reference model for evidence transitions; decide fuzz/property coverage for parser/path/size interactions and prove assertion activation and exact boundaries. Mutation checks must catch arm substitution, path escape, false activation inference, lost failures/usage and replay dependence on source files. Extend canonical specifications/test attribution with implementation, including existing effective-treatment requirements.

Implementation delivery requires independent review, clean-tree `task verify`, doctor and offline benchmark self-test. This claim has no runtime changes; its verification is distinct from implementation acceptance. A bounded live A/A procedure must predeclare controls, sample sizes, limits, acceptance criteria and interpretation before separately authorized spending. Report a calibration attempt separately from an accepted calibration outcome: provider errors, unknown activation or insufficient evidence do not automatically make the path calibrated. Until the predeclared criteria are assessed and met, label it uncalibrated and make no skill performance claims. Provider capacity failure remains an observable outcome, not permission to retry or spend automatically.
