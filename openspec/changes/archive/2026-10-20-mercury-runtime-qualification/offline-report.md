# Offline qualification result: provider usage provenance blocked

PR #64 exercised the actual Claude Code 2.1.292 → LiteLLM 1.99.0 → synthetic Chat Completions path. **The path remains unqualified for paid benchmarks:** a response with no provider usage became a successful Claude result containing numeric token counts without identifying them as estimates.

This is a concrete blocker report, not a production adapter or live Mercury result. All model responses were generated by an owned loopback fixture with fake credentials. No paid model calls occurred. The existing native adapters and frozen Gemini evidence are unchanged.

## Observed results

The supplied-count oracle was fixed by the fixture: 20 prompt tokens, including 3 cached; 5 completion tokens, including 2 reasoning. These arbitrary test counts are independent of the bridge's tokenizer.

| Case | Actual outgoing request | Provider fixture | Bridge and Claude result |
| --- | --- | --- | --- |
| `low` | `reasoning_effort: low`, `max_tokens: 1024` | Final usage-only SSE chunk: 20 input / 5 output, cached 3, reasoning 2 | 17 uncached + 3 cached / 5 output; reasoning detail becomes 0 in Claude |
| `high` | `reasoning_effort: high`, `max_tokens: 1024` | Same supplied counts | Same preserved primary totals and lost reasoning detail |
| `missing` | `reasoning_effort: low`, `max_tokens: 1024` | No usage object in any SSE chunk | Bridge emits 26 input / 4 output; Claude exits 0 and reports those counters as a successful result |

Each case produced one captured Messages request and one captured Chat Completions request. The alias changed from `mercury` to `mercury-3`; the instruction sentinel was present at both boundaries. Actual CLI requests included adaptive thinking, so low/high forwarding worked for that shape. This does not prove `instant`, disabled-thinking mapping, other request shapes, provider acceptance of the output field, or the effectiveness of a live output cap.

The two valid controls preserve **total** input and output. Losing the reasoning subset is not evidence that total output was undercounted. In the missing case, the counts first appear at the bridge boundary, before Claude. Claude also reports `provider: firstParty` and `costBasis: unknown` for the alias; its dollar estimate is not Inception billing and incurred no charge here.

The installed source supports a fallback-estimation explanation: `litellm/litellm_core_utils/streaming_chunk_builder_utils.py`, `calculate_usage`, falls back to `token_counter` when collected counts are falsey; `streaming_handler.py` publishes assembled usage. This branch attribution is source-supported inference. The missing-source → numeric-bridge → numeric-CLI sequence is directly captured.

Consequently, accepting Claude terminal counters alone cannot satisfy the requirement that missing provider usage remain unknown. A separately reviewed contract must preserve provider-side presence/provenance before fallback normalization, or a verified upstream capability must retain it. This result does not establish that real Inception omits usage, that every bridge configuration fails, or that such a contract is impossible.

## Frozen stack and isolation

[stack.json](offline/stack.json) records platform/tool versions and hashes. [selected-wheels.lock](offline/selected-wheels.lock) pins the 111 selected distributions by SHA-256. The installed arm64 wheel is `litellm-1.99.0-cp310-abi3-macosx_11_0_arm64.whl`, SHA-256 `e2b383070656fdbec4bc44602edaaed2a21e99ceee4ea0a4650c8cb381e67b59`; its three audited Python source files matched the prior source-audit hashes exactly. Python was 3.14.5, uv 0.11.16 and pip 26.1.1. The Claude executable retained the recorded 2.1.292 hash.

Distribution metadata came from [PyPI's version-specific record](https://pypi.org/pypi/litellm/1.99.0/json). Resolution and download were wheel-only with hashes; no source-build hooks ran. Wheel inspection found no `.pth`, `sitecustomize.py` or `usercustomize.py` startup files. Installation used only local wheels in a new ignored environment, with networking denied. This is metadata/startup-file inspection, not a security audit of all dependency code; uv adds its own virtual-environment bootstrap hook.

The native CLI and bridge each ran under an additional macOS Seatbelt policy. It denied all networking except the owned loopback ports, user-home file contents outside the fixture root and pinned binary, writes outside the root and an exact bridge log, and keychain service lookup. Path metadata was allowed so the interpreter could resolve its executable. Fresh child environments contained only selected settings and fake credentials; inherited proxies, API keys and subscription state were not forwarded.

Before importing the bridge, child-process probes demonstrated IPv4/IPv6 loopback access and external-address denial with `EPERM`. The final runtime policy also passed external IPv4/IPv6 and out-of-root sentinel read/write negative controls. Managed Claude policy files were absent at inspection. Actual loopback requests demonstrate the permitted path; this does not assert that remote managed policies or every filesystem/tool permission have been qualified.

`drop_params` was false; transport/router retries were set to zero. `PYTHON_DOTENV_DISABLED=1` was necessary: the initial bridge import attempted to read the ancestor repository `.env`, which the sandbox denied before its contents could be read. The supported dotenv switch removed that automatic discovery; the policy was not weakened to admit the file.

## Verification and retained failures

Run the no-network replay with:

```sh
python3 -I openspec/changes/archive/2026-10-20-mercury-runtime-qualification/offline/replay.py
```

It prints `PASS: retained evidence reproduces; provider-usage contract remains BLOCKED`. Passing verifies the evidence of the defect, not compatibility.

Decision: deterministic examples suffice for this finite research capture; no production parser, general replay API or state machine is added. Broader generated history/permission tests remain prerequisites if the route advances.

Rule: supplied 20/5 counts and cached 3 must remain distinguishable from absent usage; forwarded low/high controls must match the request.

Inputs: two adaptive-thinking controls and one missing-usage SSE response, using the standard final usage-only `choices: []` chunk for supplied counts.

Run: the packaged actual-runtime probe completed all three cases, each exit 0 with one request per boundary; offline replay passed. Full repository/check evidence is recorded at the exact delivery head in PR #64.

Mutation: three copies of the evidence independently changed known output 5→0, inserted usage into the missing fixture, and changed high→low forwarding. Replay failed at the respective named assertions; baseline and after-run passed. Verdict: **detection**, limited to the evidence checker. Original artifacts were SHA-256 checked unchanged; no bridge source or tracked fixture was overwritten.

Not covered: live Inception behavior, provider billing, full streaming semantics, tools/permissions, cancellation, malformed/partial histories, endpoint errors, native activation and production integration. No bridge-source mutation or full generated runtime suite was performed after the accounting blocker was established.

Earlier attempts remain in ignored logs. One resolver invocation rejected mutually exclusive uv flags before resolving anything. Sandbox setup initially denied the out-of-scope working directory/path metadata, and one runtime profile used unsupported address syntax; these were setup errors, not bridge defects. A 100-poll startup loop expired and was expanded to 400 polls with diagnostics. Each poll has a 0.1-second delay and a readiness-request timeout of 0.2 seconds, so the loop is bounded but is not a strict 40-second wall-clock cap. The first wire fixture put usage on the finish chunk; its output is **not** used as defect evidence. Correcting it to a separate usage-only chunk restored the supplied-count controls. The missing-usage result survived that correction and a second run of the packaged reproducer.
